### 🔴 BUG-004: 本土迂回リセット処理が直行・正規化済みルートと重複するルートを生成する

**報告日**: 2026年7月6日  
**優先度**: 🔥 高  
**ステータス**: 🧪 検証中  

#### 問題の内容
2026-07-05 の本番データで、レインボージェットの本土往復を含む `nextId` チェーンにより、同一便が検索結果に重複表示される。

- `searchRoutes("SAIGO", "HISHIURA", 2026-07-05, "08:00")` で「RAINBOWJET 西郷 18:05 → 菱浦 18:36」が2件返る
- `searchRoutes("SAIGO", "BEPPU", 2026-07-05, "08:00")` で「RAINBOWJET 西郷 18:05 → 別府 18:49」の単一セグメントに加え、同一船を「西郷→菱浦」「菱浦→別府」の2セグメントに分けた実質重複ルートが返る
- 検索時刻 12:00 では重複しないため、午前の本土行きから戻るチェーン処理が発生条件になっている

#### 原因
`findTransferRoutes` の `isDetourToMainland` 分岐は、島内移動で本土へ寄って出発地に戻る便から、本土区間を捨てて「出発地へ戻った後の区間」だけを resume ルートとして生成する。

この処理は BUG-001 の本土経由除外を補うための例外だが、resumeTrips に本土 `via` フラグがない通常データでは、同じ区間が `findDirectRoutes` または同一船チェーンの正規化ですでに発見される。そのため、resume 分岐が不要なルートを追加し、単一セグメントの完全重複または同一船の分割重複を生んでいる。

#### 期待される動作
resume 分岐は、resumeTrips のいずれかが「`via` が本土、かつ出発・到着がどちらも本土ではない」行で、通常の直行検索・正規化では除外されるケースにだけ使う。via フラグがない通常チェーンでは、通常経路の結果だけを表示する。

#### 解決方法
`src/composables/useRouteSearch.ts` の `isDetourToMainland` resume 分岐で、resumeTrips に本土 `via` フラグ付きの島内区間が含まれる場合のみルート生成するガードを追加しました。

`src/test/unit/composables/useRouteSearch.test.ts` に、レインボージェット 93〜98 の本番データ形状で重複が出ないことと、via 本土フラグ付き resume ケースは引き続き結果に含まれることを検証する回帰テストを追加しました。

#### 実データ再検証（2026年7月14日）

通常Chromeでdev公開版を確認し、西郷→菱浦ではレインボージェット18:05→18:36が1件、西郷→別府では18:05→18:49が1件の単一セグメントとして表示され、重複がないことを確認しました。リリースSHA固定後の再確認を残すため、ステータスは検証中を維持します。

### 🔴 BUG-003: 直行便が5件以上あると乗換探索がスキップされ、より早い通し乗車・乗換ルートが漏れる

**報告日**: 2026年7月6日  
**優先度**: 🔥 高  
**ステータス**: 🧪 検証中  

#### 問題の内容
`searchRoutes` は直行便が5件以上見つかると `findTransferRoutes` を実行しない（`src/composables/useRouteSearch.ts` の `if (directRoutes.length < 5)`）。同一船の nextId チェーンをまたぐ「通し乗車」（例: いそかぜの巡回便で菱浦→別府→来居と乗り続ける）は `findTransferRoutes` 内の正規化でしか発見できないため、直行行が5件以上あるペアではより早く着くルートが表示されない。

2026-07-05 の本番データでの実例（独立実装の最適経路探索との全ペア×5時刻=140クエリ突き合わせで検出）:

| 区間・検索時刻 | アプリ最速 | 実際の最速 | 差 |
|---|---|---|---|
| 来居→菱浦 08:00発 | 10:31発 → 10:49着 | いそかぜ 08:05発 →(別府経由 通し乗車)→ 08:32着 | 2時間17分 |
| 別府→来居 08:00発 | 09:51着 | いそかぜ 08:25発 →(菱浦経由 通し乗車)→ 08:52着 | 59分 |
| 菱浦→来居 05:00発 | 08:52着 | いそかぜ 07:37発 →(別府経由 通し乗車)→ 08:03着 | 49分 |
| 来居→別府 05:00発 | 08:22着 | いそかぜ 07:17発 →(菱浦経由 通し乗車)→ 07:44着 | 38分 |

いずれも島前内航路（いそかぜ巡回）の区間で、島民の日常利用に影響する。

#### 原因
- `findDirectRoutes` は時刻表の単一行しかマッチしない
- 行境界をまたぐ通し乗車は `findTransferRoutes` の `shouldNormalizeTrips` 正規化で生成される
- しかし直行行が5件以上あると `findTransferRoutes` 自体がスキップされる

#### 期待される動作
直行便の件数に関わらず、同一船チェーンの通し乗車ルートは常に探索する。乗換探索を常時実行した上で、結果のノイズ（直行より遅く着く劣後ルート）は別途フィルタリングで制御するのが望ましい。

#### 解決方法
`src/composables/useRouteSearch.ts` の `searchRoutes` で、直行便件数による `findTransferRoutes` のスキップ条件を撤廃しました。これにより、直行行が5件以上ある区間でも、`nextId` チェーンをまたぐ同一船の通し乗車が常に正規化候補として探索されます。

乗換探索の常時実行で増えるノイズに対しては、結果の後処理として劣後乗換ルートのフィルタを追加しました。

- 除去対象は2セグメント以上の乗換ルートのみ
- 支配側は欠航セグメントを含まない単一セグメントルート（直行行または正規化済み通し乗車）のみ
- 単一セグメントルートが乗換ルートより遅く出発でき、かつ同時刻または早く到着できる場合だけ除去
- 欠航セグメントを含む乗換ルートは表示維持のため除去しない
- 乗換ルート同士では支配判定しないため、BUG-002 の境港→菱浦 3ルートは維持

`src/test/unit/composables/useRouteSearch.test.ts` に、来居→菱浦 08:00発で `218-219` の通し乗車が返ること、直行系に支配される乗換だけが除去されること、欠航セグメントを含む乗換が除去されないことを検証する回帰テストを追加しました。

#### 実データ再検証（2026年7月14日）

通常Chromeでdev公開版の来居→菱浦（2026-07-05、08:00発）を確認し、いそかぜ08:05→08:32の通し乗車が検索結果の先頭に表示されることを確認しました。リリースSHA固定後の再確認を残すため、ステータスは検証中を維持します。

#### 補足（同時に監査して問題なしを確認した観点）
- 到着時刻指定モード（isArrivalMode）: 境港→菱浦 by 18:00 で別府乗換2件のみ返る等、正常
- HONDO（本土）エイリアス展開: 正常
- 車両検索（withCar）: しらしまチェーンの通し乗車正規化を含め正常
- 2回乗換（異なる船×3本）が必要なケース: 2026-07-05 のデータでは存在しない

### 🔴 BUG-002: 乗換案内で同一船の経由港での乗り換えルートが検索されない

**報告日**: 2026年7月5日  
**優先度**: 🔥 高  
**ステータス**: 🧪 検証中  

#### 問題の内容
2026年7月5日の境港→菱浦の検索で、来居乗り換えの1ルートしか表示されない。フェリーしらしまに乗ったまま別府まで行き、別府で内航船に乗り換えるルート（より早く到着する）が表示されない。

- ⭕ 表示される: 境港 14:10 →(しらしま)→ 来居 16:35 ／ 来居 17:49 →(いそかぜ)→ 菱浦 18:07
- ❌ 表示されない: 境港 14:10 →(しらしま・来居経由)→ 別府 17:10 ／ 別府 17:20 →(いそかぜ)→ 菱浦 17:27
- ❌ 表示されない: 同上 ／ 別府 17:40 →(フェリーどうぜん)→ 菱浦 17:52

#### 当初の原因（検索結果生成、修正済み）
`src/composables/useRouteSearch.ts` の `findTransferRoutes` は「1本目 = 時刻表の単一行」＋「2本目 = 同一船の nextId チェーン（目的地到達必須）」という構造のため、乗換地点が1本目の行の到着港（この場合は来居）に固定される。1本目の船の継続区間（しらしま 来居→別府）に乗り続けて経由港（別府）で別の船に乗り換えるルートを生成できない。

2026/03/09〜05/31 の時刻表では境港発の行が「境港→別府」の1行だったため別府乗換が検索できていたが、2026/06/01〜08/07 の時刻表では「境港→来居」「来居→別府」の2行に分割されたことで、この構造上の制約が顕在化した（コード変更による退行ではなくデータ形状起因）。

#### 期待される動作
1本目の便が同一船で先の港へ継続する場合（nextId チェーン）、チェーン上の各経由港でも乗り換え候補を探索し、別府乗換ルートも結果に含める。

#### 当初の修正内容
`src/composables/useRouteSearch.ts` の `findTransferRoutes` に、1本目の便を同一船の `nextId` チェーンで継続した到着港を追加の乗換候補として探索する処理を追加しました。

- 従来どおり単一行の到着港（来居）での乗換探索を維持
- しらしまに乗り続けた先の別府も乗換候補に追加
- 継続乗船した1本目は `39-40` のような1セグメントに正規化し、運賃は境港→別府で計算
- 既訪問港へ戻る候補や本土経由の除外条件は維持

`src/test/unit/composables/useRouteSearch.test.ts` に本番時刻表抜粋の回帰テストを追加し、境港→菱浦で来居乗換1件、別府乗換2件の合計3ルートが返ることを検証しています。

#### 実データ再検証（2026年7月14日）

通常Chromeでdev公開版の境港→菱浦（2026-07-05、08:00発）を確認したところ、期待する3件に対して別府17:20発のいそかぜへ乗り換える1件しか表示されませんでした。来居17:49発、別府17:20発、別府17:40発の各候補に必要な便はdev Storageの実時刻表に存在するため、データ欠落ではなく検索結果生成または後処理の問題として再調査します。実データ受入は不合格で、BUG-002は未解決です。

#### 詳細調査結果（2026年7月14日）

結論として、残存不具合の原因は検索結果生成ではなく、`src/pages/transit.vue` の画面表示用 `sortedResults` にある同一出発時刻フィルタです。

- dev Storageの実時刻表には、境港14:10発のしらしま（`979`→`980`）と、来居17:49発いそかぜ（`570`）、別府17:20発いそかぜ（`568`）、別府17:40発フェリーどうぜん（`782`）が存在し、すべて2026-07-05に有効
- 実時刻表をストア形式へ変換し、アプリと同じ `searchRoutes` を直接実行すると、来居乗換1件と別府乗換2件の合計3件を返す
- 3件の経路シグネチャは異なるため、`useRouteSearch.ts` の経路・船種単位の重複排除では削除されない
- その後 `transit.vue` の `sortedResults` が、経路・乗換港・船種・運賃・運航状態を考慮せず、ルート全体の出発時刻だけでグループ化し、各グループから最も早く到着する1件だけを残す
- 3件はいずれも境港14:10発のため同じグループとなり、別府17:20発いそかぜへ乗り換えて17:27に着く1件だけが残り、別府17:52着と来居18:07着の2件が画面表示前に削除される
- このフィルタは並び替え処理より先に実行されるため、「おすすめ」「時間が短い」「料金が安い」「乗換が少ない」の全モードで1件のまま。通常Chromeのdev公開版でも4モードすべて同じ1件だけになることを確認

この同一出発時刻フィルタは2025-11-30の `9a8e51d2`（`feat(transit): 乗換案内の結果並び替えを改善`）で追加され、ページ単体テストにも「同一出発時刻では最速到着1件だけを残す」という期待値が明示されています。一方、2026-07-06の `a432e45` で追加したBUG-002回帰テストは `useRouteSearch` 単体までしか通しておらず、ページ側の後処理を含む受入条件を検証していません。旧仕様とBUG-002の「異なる乗換港・船を有効な代替経路として残す」という要件が衝突したまま、テスト階層間の隙間で見逃された状態です。

影響範囲はBUG-002の3件に限りません。同じ出発時刻を持つ正当な代替経路は、乗換港、船種、料金、乗換回数、運航状態が異なっていても全画面ソートモードで非表示になります。最速経路が欠航で、同時刻発の遅い有効経路がある場合も、有効経路を隠す可能性があります。

修正時は、画面側の出発時刻だけによるフィルタを撤廃して `useRouteSearch` の経路シグネチャ単位の重複排除へ一本化するか、少なくとも経路・船種・運航状態を含む同値条件に狭める必要があります。また、実時刻表相当の3件を `transit.vue` の `sortedResults` まで通し、全並び替えモードで維持されるページ回帰テストが必要です。

#### 追加修正（2026年7月14日）

`src/pages/transit.vue` の `sortedResults` から、同一出発時刻の候補を最速到着1件へ絞る画面側フィルタを撤廃しました。重複排除は `useRouteSearch` の経路・船種を含むシグネチャ単位の処理へ一本化し、画面側では検索結果全件を選択中の並び替え条件でソートします。

`src/test/unit/pages/transit.test.ts` には次の回帰テストを追加・更新しました。

- 同一出発時刻でも異なる経路を有効な代替候補として維持する
- BUG-002の来居乗換1件・別府乗換2件をページの `sortedResults` まで通す
- 「おすすめ」「時間が短い」「料金が安い」「乗換が少ない」の全4モードで3件を維持する
- 到着時刻指定やおすすめ順の同時刻候補も、到着時刻・乗換回数・運賃の比較対象として残す

#### 修正後検証（2026年7月14日）

dev Storageの実時刻表1,068件を一時的なローカルStorage Emulatorへ読み込み、通常Chromeで境港→菱浦（2026-07-05、08:00発）を再確認しました。17:27着（別府・いそかぜ）、17:52着（別府・フェリーどうぜん）、18:07着（来居・いそかぜ）の3件が表示され、全4ソートモードで3件が維持されることを確認しました。

### 🔴 BUG-001: 乗換案内で本土を経由する経路が表示されている

**報告日**: 2025年1月20日  
**解決日**: 2025年1月21日  
**優先度**: 🔥 高  
**ステータス**: ✅ 完了  

#### 問題の内容
隠岐諸島内での移動を検索すると、わざわざ本土（七類港や境港）を経由する遠回りな経路が表示されてしまいます。

例えば、西郷港から菱浦港への移動で：
- ❌ 西郷 → 七類（本土） → 菱浦（所要時間：半日以上）
- ⭕ 西郷 → 菱浦（フェリーどうぜんで直行：約1時間）

#### 再現方法
1. 乗換案内ページを開く
2. 出発地：西郷、目的地：菱浦を選択
3. 検索ボタンをクリック
4. 結果に本土経由の非効率な経路が含まれている

#### 期待される動作
- 島内移動では、まず直行便を優先表示
- 本土経由は、直行便がない時間帯のみ表示
- 所要時間が極端に長い経路は除外するか、警告を表示

#### 影響
利用者が誤って非効率な経路を選択してしまう可能性があり、旅行計画に大きな支障をきたす。

#### 解決方法
`src/composables/useRouteSearch.ts`の`findTransferRoutes`関数に、島内移動時に本土経由ルートを除外するロジックを追加しました。

```typescript
// Prevent routes that go through mainland when traveling between islands
if (
  !isMainlandPort(departure) &&
  !isMainlandPort(arrival) &&
  (isMainlandPort(firstTrip.arrival) || isMainlandPort(secondTrip.departure))
) {
  continue;
}
```

これにより、島嶼間の移動で本土を経由する非効率な経路が検索結果から除外されるようになりました。
