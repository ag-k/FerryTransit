# 隠岐汽船の7日先運航見通し

更新日: 2026-11-24

この文書は、予報を収集する保守担当者と、運航予測モデルを作る開発者向けです。まず「取得と再計算」を実行し、学習へ進む際は「学習データの契約」以降を確認してください。

現在は、明日から7日後までの波・風を保存し、欠測と計画休航を区別する試作です。**運航予測は未算出で、欠航確率は常に `null`** です。既存の翌日リスク表示と本番配信には接続していません。

## 1. 取得と再計算

リポジトリのルートで、Node.js 22系（22.23以上）を使います。収集スクリプトは Node の TypeScript 読み込み機能で集計処理を呼ぶため、別のビルドは不要です。

```bash
# 無料公開APIを使う、1回限りの評価用取得
npm run forecast:collect -- --evaluation

# 保存した入力を使って、通信せずに再計算
npm run forecast:collect -- --input output/weekly-outlook/<snapshotId>/snapshot-input.json --output output/weekly-outlook-replay

# オプションと契約APIの設定方法を表示
npm run forecast:collect -- --help
```

`--output` は保存先の親ディレクトリです。その下に新しい `<snapshotId>` を作るため、再計算でも既存結果を上書きしません。`--input` と `--evaluation` は併用できません。自動定期実行はまだありません。

実取得では、`output/weekly-outlook/<snapshotId>/` に次を保存します。

| ファイル | 内容 |
| --- | --- |
| `manifest.json` | 取得条件、取得日時、応答コード、再試行、出典、時刻表の対象期間 |
| `raw/*.json` | 提供元の応答、要求パラメータ、失敗理由。認証情報は除去 |
| `points.json` | 今回使用した代表点の設定 |
| `snapshot-input.json` | 集計処理へ渡した完全な入力。再計算の起点 |
| `outlook.json` | 日本時間の翌日から7日後までの集計結果 |

再計算では `manifest.json`、`snapshot-input.json`、`outlook.json` を保存します。元の取得日時を維持するので、同じ入力から同じ見通しを再現できます。再計算時点の最新予報には更新されません。

Open-Meteo の料金ページは無料枠での評価・試作を案内していますが、Free API の規約は非商用利用に限定しています。`--evaluation` は商用利用の許可を意味しません。商用の本番利用に進む前に契約APIへ切り替えます。[料金](https://open-meteo.com/en/pricing)と[利用規約](https://open-meteo.com/en/terms)を確認し、契約で指定された `OPEN_METEO_API_KEY`、`OPEN_METEO_MARINE_URL`、`OPEN_METEO_WEATHER_URL` を環境変数に設定してください。契約APIを使う場合は `--evaluation` を付けません。キーをコードや保存データに含めないでください。

## 2. 今回実装した集計

入口は [collect-weekly-outlook.mjs](../../scripts/forecast/collect-weekly-outlook.mjs)、集計は [weeklyOutlook.ts](../../src/utils/weeklyOutlook.ts) の `buildWeeklyOutlook(input)` です。集計関数は時刻やネットワークを参照せず、渡された入力だけで結果を返します。

| 対象 | 取得・集計方法 |
| --- | --- |
| 波 | ECMWF WAM (`ecmwf_wam`) と GFS Wave (`ncep_gfswave025`) の有義波高、波向、周期 |
| 風 | ECMWF IFS (`ecmwf_ifs025`) と GFS (`gfs_seamless`) の10m風速・風向・突風。風速単位は m/s |
| 地点 | 本土沖、本土・隠岐中間、隠岐諸島南側の試験点3か所。設定は [forecast-points.json](../../scripts/forecast/forecast-points.json) |
| 期間 | `forecast_days=8`、`timezone=Asia/Tokyo`、`timeformat=unixtime`。時刻はUTCのUnix秒として読み、日本時間の日付で翌日〜7日後を切り出す |
| 日別値 | 地点・モデルごとの日最大波高、日最大風速、日最大突風。波高最大時の波向・周期、風速最大時の風向も保存 |
| 品質 | 地点・モデル・日ごとに24時間の値、単位、時刻重複などを確認。`complete` / `incomplete` / `unavailable` / `stale` を付与 |
| 当日の公式情報 | `https://ship.nkk-oki.com/api/status` を1回取得し、`currentOfficialNotice` と原応答へ保存 |

APIの定義は [Marine Weather API](https://open-meteo.com/en/docs/marine-weather-api) と [Weather Forecast API](https://open-meteo.com/en/docs) を参照してください。有義波高の予報格子値は港内の波高と一致するとは限りません。要求した座標とAPIが選んだ格子座標の両方を残します。要求地点から100 kmを超えて離れた応答は、別地域のデータの取り違えとして使用しません。この距離は異常な応答を検出する上限であり、航路の代表性や予報精度の基準ではありません。

日最大値は日本時間の0〜24時を対象にします。航行中の最大値ではなく、風と波の最大時刻も別々です。代表点は実際の航跡や港の遮蔽を検証していないため、便単位の判定にはまだ使えません。

`complete` は必要な値がそろった状態を表し、予報精度を保証しません。取得から収集完了まで12時間を超えた入力は `stale` とします。これは入力の鮮度検査で、モデル初期時刻の検査ではありません。現在のAPI応答から初期時刻を確定できないため、`modelRunAt` は `null` です。`fetchedAt` で代用しません。

モデル間比較は、同じ地点で両モデルの値が完全な場合だけ計算します。その最小値・最大値・差は、2つの決定論的予報の違いです。信頼区間や欠航確率として表示しません。

### 出力状態の読み方

`days[].vessels.ferry` と `days[].vessels.rainbowjet` は、以下の `predictionStatus` を返します。

| 値 | 意味 | 表示する場合の文言 |
| --- | --- | --- |
| `planned_suspension` | 出典のある計画休航 | 計画休航 |
| `schedule_unknown` | 時刻表の対象外・欠落・未対応の予定形式 | 運航予定を確認できません |
| `insufficient_data` | 予定はあるが予報が不足・期限切れ | 予報データ不足・運航予測未算出 |
| `awaiting_calibration` | 予定と予報はそろったが、モデルは未学習 | 運航予測未算出 |

すべての状態で `cancellationProbability: null`、`calibrationStatus: "uncalibrated"` を維持します。欠測や時刻表不明を、欠航確率0%へ変換しません。

時刻表は [oki-kisen-2026.json](../../gtfs/raw/ferry/oki-kisen-2026.json) の各 `schedule` を日付と船種で照合します。レインボージェットの **2026-12-01〜2027-02-28のドック休航** は、[公式時刻表PDF](https://www.oki-kisen.co.jp/files/original/202611111303087864c7b17dc.pdf)を根拠に別ルールで保持しています。2027-03-01以降など、資料の対象外を計画休航扱いにはしません。この期間指定は毎年の自動更新ではなく、次の公式資料が出た際に見直す必要があります。

公式APIの当日の発表は7日分の集計と分離して保存します。当日の「定期運航」を翌日以降へ引き継ぎません。正式発表を表示に使う拡張では、対象日・船種・便の適用範囲を確認します。

## 3. 既存の翌日モデルを流用できない理由

現在の処理は、[status.vue](../../src/pages/status.vue) → [wave.ts](../../src/utils/wave.ts) → [cancelRisk.ts](../../src/utils/cancelRisk.ts) → [cancel_models.json](../../src/assets/models/cancel_models.json) です。フェリーとレインボージェットのロジスティック回帰に、波高2値だけを渡しています。

| 監査項目 | 現状と必要な確認 |
| --- | --- |
| 波高2値の意味 | `tomorrow_wave` の文字列から先頭2つの数値を取り、1つなら複製する。時刻の定義や航路最大値という契約はない |
| 新しい予報との互換性 | 毎時予報の平均・最大値を既存の `m1` / `m2` へ代入すると特徴量の意味が変わるため、係数を流用しない |
| 教師ラベル | メタデータは `rainbowjet_state`、既存API・DB仕様は `fast_ferry_state`。学習時の写像を確認する |
| 欠航の扱い | メタデータのルールは文字列中の「欠航」などに依存する。部分欠航、理由、計画休航の扱いを元データと学習コードで確認する |
| 評価の再現性 | リポジトリでは学習コード、学習期間・件数、時系列分割、確率校正、リードタイム別の評価を確認できていない |

UIのリスク段階に使う確率の境界値は、船舶の運航中止基準ではありません。隠岐汽船の公式資料から船種・港別の風速・波高の数値基準を確認できていないため、新しい閾値を仮の運航規則として設けません。

隠岐汽船の[波情報についてのFAQ](https://www.oki-kisen.co.jp/faq/84)も、掲載値が主に気象庁の予報によることを説明しています。履歴にある波の文字列を、その日の観測値や7日前の予報として扱わないことが必要です。

## 4. 学習データの契約

以下は次段階の設計です。今回の出力を、そのまま学習データ完成版とは扱いません。

まず、既存の `ferry_states` 履歴と学習コードを取得して、翌日モデルを再現します。[既存API仕様](../status-api/api-status.md)に合わせ、少なくとも `id`、`date`、`ferry_state`、`ferry_comment`、`fast_ferry_state`、`fast_ferry_comment`、`today_wave`、`tomorrow_wave` を原文で受け取ります。存在する場合は `created_at` / `updated_at` と更新履歴も付け、エクスポート日時を記録します。当日向けAPIから過去の履歴を取得できるとは仮定しません。

| データ群 | 保存する項目・区別 |
| --- | --- |
| 予報の来歴 | スナップショットID、収集日時、取得日時、予報モデル、モデル初期時刻、出典URL、原応答。取得時に分からない初期時刻は `null` |
| 予測の対象 | 対象日、対象時刻、船種、便ID、出発・到着・寄港地。便IDは対象日と組にして識別 |
| 予報の先行時間 | JSTの日付差と、予測を利用できた時点から対象時刻までの時間差を別々に保持。`daysAhead=7` を固定の168時間と同一視しない |
| 気象値 | 要求座標・採用格子座標、毎時の波高・波向・周期・風・突風、単位、欠測・品質。将来追加するアンサンブルはメンバー番号も保持 |
| 運航予定 | 時刻表の出典・有効期間・版、予定便、実際の配船、計画休航。代船運航と欠航を分離 |
| 公式発表 | 発表時刻、取得時刻、適用日・便、原文、訂正履歴。発表と、その後実際に運航した結果を分離 |
| 運航結果 | 全便運航、全便欠航、部分欠航、寄港中止、港変更、時刻変更、計画休航、不明。原因は気象・機関故障等・不明を分ける |
| 管理情報 | ラベル規則の版、特徴量定義の版、モデル版、確認者、原データとの対応。原文を後から再分類できる形で保持 |

公式の[運航状況](https://www.oki-kisen.co.jp/situation/)には「定期運航」「運航に変更あり」「欠航」があります。見出しだけでは当日全便の実績を確定できないので、コメントと発表の適用範囲を残します。[運送約款](https://www.oki-kisen.co.jp/yakkan/388)にも、気象以外を含む運航・寄港・船舶変更の事由があります。

最初に作る目的変数は、取得できる実績の粒度に合わせます。船種・日単位の履歴しかなければ「その日に気象による運航変更・欠航があったか」を検討し、便別確率とは表示しません。原因不明や判定不能を正常運航の負例にせず、計画休航は気象モデルの学習・評価から除きます。部分欠航と全便欠航をまとめる場合は、目的変数名と表示にもその定義を明示します。

## 5. 7日先モデルの作り方と評価

予報の評価には、対象日の7日前など、**その時点で利用できた予報**を使います。[Historical Forecast API](https://open-meteo.com/en/docs/historical-forecast-api)は各予報実行の先頭部分をつないだ時系列で、対象日のデータを取るだけでは7日前の予報を再現できません。[Single Runs API](https://open-meteo.com/en/docs/single-runs-api)で初期時刻を指定するか、今回のように当時の応答を保存します。過去の波浪モデル・変数・期間が取得できるかは別途確認が必要です。利用できない履歴を再解析値で埋めてD+7の成績としません。

将来の特徴量は、便の出発〜到着時間に対応する航路上の波・風、波向・周期、港へ吹き込む風、船種、季節、予報先行時間を候補にします。まず日別モデルを基準に置き、便・港別の実績がそろってから細分化します。風向・波向は循環量として扱い、モデル間差も特徴量の候補にとどめます。

評価は次の順で行います。

1. **期間で分割する。** 過去で学習し、その後の期間で検証する。同じ荒天期間や同じ対象日の別予報を学習側と評価側に散らさない。校正用データも最終評価用と分ける。
2. **比較対象を置く。** 船種・季節別の過去頻度などを基準に、改善の有無を確かめる。既存翌日モデルとの比較は、入力・目的変数を再現できる範囲で行う。
3. **D+1〜D+7、船種別に測る。** Brier score、信頼度曲線による確率校正、欠航の再現率、適合率、誤警報率を確認する。評価件数と欠航件数も並べ、少数例の高精度を過大評価しない。
4. **公開条件を決める。** 欠航の見逃しと誤警報の影響を踏まえて判定境界を選ぶ。データ不足、期限切れ、予定不明は別表示にし、長い先行時間で性能が不足する場合は確率表示の対象から外す。

収集時点のモデル初期時刻が不明でも、保存済み応答は「その取得時点で使えた予報」として検証できます。ただし、初期時刻を基準にした予報時間別の評価とは区別します。学習・校正が終わるまで、現在の `null` を推測値で埋めません。

## 6. 段階的な統合

| 段階 | 作業と完了条件 |
| --- | --- |
| 今回 | 1回の収集、原応答保存、7日分の集計、再計算。公開UI・定期処理・デプロイは未接続 |
| 履歴の確認 | `ferry_states` の履歴と学習コードを取得し、ラベルの写像、予報の時点、既存モデルの評価を再現する |
| データ蓄積 | 契約条件を確定し、予報と公式発表の更新履歴を保存する。便別の実績を確保できるか確認する |
| モデル検証 | 時間順の評価、船種・先行時間別の校正、既存表示に影響しない並行検証を行う |
| 配信・表示 | Cloud Scheduler / Functions → Firebase StorageのJSON → Nuxt静的アプリの構成で接続する。予報専用のパス・キャッシュ・スキーマ版を設ける |
| 公開 | 取得日時、対象期間、公式発表、予測、計画休航を区別して表示し、期限切れと取得失敗を確認する。リポジトリのリリースQAを経て公開する |

上記の定期収集・配信構成は設計案で、稼働していません。本番Webは静的配信なので、NuxtのサーバーAPIを追加するだけでは定期収集を実行できません。予測から既存の実運航ステータスや経路検索の欠航判定を書き換えず、予報専用の参照データとして接続します。APIキーはサーバー側に保持し、公開JSONと画面に Open-Meteo、ECMWF、NOAA/NCEP の出典を表示します。[提供元表記の要件](https://open-meteo.com/en/docs/marine-weather-api)も確認してください。

次の着手点は **既存履歴と学習コードの確認** です。これにより、学習できる対象が日別の欠航言及なのか、気象による実際の運航変更なのかを確定できます。
